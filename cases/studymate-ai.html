StudyMate AI

A study workspace that explores how focused AI assistants can support coding, design, UX, exams and project planning without making students write a new role prompt every time.

View static prototype View code

Problem

A general chatbot can give broad answers that feel disconnected from a student's actual task and level.

Primary users

Multimedia Design students working with code, design, UX, exams and project planning.

My contribution

Product concept, UI design, frontend, backend structure, prompt configuration, documentation and deployment preparation.

Stack

HTML, CSS, JavaScript, Node.js, Express, a local OpenAI API integration and Markdown knowledge files. Cloudflare Pages Functions are prepared for deployment.

Overview

Project overview

Implemented locally

The interface, assistant selection, prompt suggestions, chat states and Express backend routes are implemented. With a local API key, the server can send protected requests to OpenAI.

Public functional prototype

The public GitHub Pages demo demonstrates the complete interface flow with static fallback responses. It does not run the server-backed OpenAI integration.

Not a finished commercial product

StudyMate AI is not production-ready. Public server deployment, live OpenAI testing, stronger abuse protection and external usability testing still need to be completed.

Context

Users and use case

One clear task before the message

The main user is a Multimedia Design student who may need help with very different tasks during the same project. Choosing a focused assistant makes the intended kind of help visible before the conversation begins.

Less prompt setup

The student should not need to explain “act as a coding mentor” or “review this as a UX researcher” in every message. The selected role and its supporting instructions are handled by the system.

Secondary audience

The case also needs to help a recruiter understand what is real: a working interface, server-side routes and structured prompts, presented with clear prototype limits.

AI UX

Product concept

Six user-facing assistants keep the product understandable. Internal skill instructions and relevant project context can then shape the response without adding more choices to the interface.

  • Study CoachExplains difficult topics and helps structure study work.
  • Coding MentorSupports HTML, CSS, JavaScript, APIs, JSON and debugging.
  • Design CriticReviews hierarchy, spacing, visual choices and accessibility.
  • UX ResearcherHelps plan research, user journeys and evidence-based testing.
  • Exam CoachChallenges arguments and prepares realistic project questions.
  • Project ManagerTurns project needs into priorities, tasks and simple sprint plans.

Familiar chat patterns

Assistant navigation, example prompts, message bubbles and copy/retry actions reduce the amount of new interaction the user has to learn.

Visible system state

The frontend includes empty, loading, error, retry and static fallback states. The fallback explains the prototype boundary instead of pretending a generated answer came from OpenAI.

Context without debug noise

The interface can show that project knowledge is available, while matched files and hidden prompt instructions remain a backend concern.

Software structure

Technical architecture

The browser manages the experience. A server-side route owns validation, prompt context, the secret key and the OpenAI request.

Implementation

Frontend and backend implementation

Frontend state and feedback

Vanilla JavaScript manages assistant selection, prompt suggestions, local chat state and the loading, error, retry and static fallback states. The message composer is disabled while a response is pending.

Protected request flow

The frontend sends only assistantId and the user message. The API key never appears in frontend JavaScript; it belongs in the Express environment or Cloudflare environment variables.

Prompt and context building

The server combines the assistant role, internal skill instructions, relevant Markdown context and the user message. The local Knowledge Base uses weighted keyword and phrase matching, not embeddings or semantic search.

Tradeoffs

Challenges and current limitations

Static and server modes can be confused

A public interface that looks complete can make a fallback answer feel like an error. I rewrote the static response so it explains what the prototype demonstrates and what is not connected.

Context matching is intentionally simple

The Knowledge Base uses weighted keyword and phrase matching across Markdown files. It is understandable and suitable for this prototype, but it is not semantic retrieval and can miss useful context.

Prototype protection is limited

There are no real accounts, database or cloud chat history. Rate limiting is basic, and the prepared Cloudflare integration still needs public deployment testing before it can be described as a live AI service.

Internal walkthrough before external testing

Testing and iteration

Internal walkthrough

I reviewed five tasks myself: understand the concept, enter the demo, choose an assistant, submit a Multimedia Design task and start a new chat. This was an internal check, not external user research.

What changed

The walkthrough showed that fallback copy could sound like a backend error and link-based questions could be misleading. I rewrote the fallback, added URL-aware guidance and reduced the visual weight of user messages and copy actions.

Technical checks

The repository includes a deployment-preparation check for required routes, protected frontend code, Cloudflare configuration, rate limiting and Knowledge Base context. This checks implementation structure, not product usability.

Usability testing plan

Can students understand and use the assistant system?

Status: Planned — external testing has not yet been completed.

Objective and participants

Test whether 3–5 Multimedia Design students or students familiar with digital study tools can understand the assistant roles, complete the main chat flow and recognise the limits of the static demo.

Tasks

  1. Explain what StudyMate AI is for.
  2. Enter the demo and select a suitable assistant.
  3. Submit a realistic study task.
  4. Start a new chat.
  5. Explain what the static fallback means.

Observe and measure

Record task completion, critical errors, moderator assistance, hesitation or wrong turns, and participant comments. Pay particular attention to assistant selection and whether the fallback is mistaken for a broken feature.

Pending evidence

Findings: Pending external sessions. Resulting design changes: Pending analysis of the completed test notes.

Next validation step

Test the prototype with 3–5 Multimedia Design students and observe whether they understand the assistant structure, project context and core interaction without guidance.

Outcome

Result and reflection

Current result

The result is a functional prototype that connects a product idea, six clear assistant roles, frontend interaction states and a protected server-side request structure.

What I learned

The most useful AI decision was not adding more features. It was deciding where roles, context, secrets and feedback states belong so the interface stays understandable.

Next improvements

My next steps are to verify the Cloudflare deployment with a real key, run the planned sessions with 3–5 participants, improve the weakest flow based on evidence and add more relevant project summaries to the Knowledge Base.
